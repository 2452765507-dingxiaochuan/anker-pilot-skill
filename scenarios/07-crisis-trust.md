# 3G｜舆情 / 危机 / 信任修复（深度专业包）

**先读案例包**：`../references/scenario-case-packs/07-crisis-trust-cases.md`

## 适用题型
产品安全、隐私争议、质量问题、召回、负面舆情、错误信息、媒体质疑、平台危机、信任修复。

## 前置原则
安全、法律与监管要求优先于传播目标。题目若涉及现实中的重大安全/法律事项，应明确哪些判断需要法务、质量、研发或监管确认。

## A｜事实中心 + 风险分级 + 前 2 小时动作
```text
先建立唯一事实中心【Single Source of Truth】。只写：
- 已确认事实；
- 尚未确认；
- 信息来源和时间；
- 受影响对象/范围；
- 潜在安全、隐私、法律、业务影响；
- 谁负责继续验证；
- 下一次更新时间。

按“伤害严重度 × 扩散速度 × 不确定性 × 可逆性”做风险分级。

随后给前 30 分钟 / 2 小时 / 24 小时行动清单，分别覆盖：停止继续风险、用户指引、内部升级、证据保存、客服、渠道/平台、监管/合作方沟通、公开信息占位。

每个动作写负责人和触发条件。

成功标准：团队先降低真实风险，并让用户清楚下一步，不因为急于发声明而放大错误信息。
```

## B｜利益相关者回应 + 信息节奏
```text
分别为：受影响用户、普通用户、员工、客服、媒体、零售/渠道伙伴、平台、监管/合作伙伴建立沟通表。

每类回答：
他们此刻最担心什么 / 我们已知道什么 / 他们需要采取什么行动 / 哪些信息暂不能确认 / 通过什么渠道 / 下一次更新时间。

公开表达建议使用：
事实 → 当前行动 → 对受影响者的帮助/补救 → 调查/验证 → 下一次更新。

生成：首份 holding statement、FAQ、客服话术、内部员工通知、媒体 Q&A。保持事实核心一致，但允许细节按对象变化。

成功标准：不同渠道不打架；用户能找到行动信息；对未知部分明确写“正在确认 + 下一次更新时间”。
```

## C｜调查证据 + 第三方验证 + 更新机制
```text
设计调查和证据计划：研发/质量检查、批次/日志、用户样本、第三方实验/审计（适用时）、监管沟通、供应链追踪。

为每个关键争议点建立“什么证据才能改变当前判断”。

每次有新证据时：
1）更新事实中心；
2）判断是否改变用户行动建议；
3）同步 FAQ / 官网 / 社媒 / 客服 / 媒体；
4）记录版本与时间；
5）说明旧说法为何调整。

技术/安全争议需要第三方时，选择具有实际专业资格和可复查方法的机构，而非只做背书 Logo。

成功标准：信息越来越接近事实，所有渠道使用同一最新版本。
```

## D｜补救设计 + 30/60/90 天信任恢复
```text
把恢复计划落到可观察改变：
产品/流程整改、召回/更换/退款、客服资源、质量门槛、第三方验证、透明机制、员工/渠道培训、持续用户沟通。

给 30/60/90 天路线：每阶段必须完成的事实验证、用户补救、流程改变、公开证明和管理层复盘。

建立指标：投诉/退换趋势、客服解决率、重复问题率、负面主题变化、媒体语义、用户调查、复购/留存、整改完成率等。

说明什么结果代表可以逐步恢复常规传播，什么信号代表仍需继续整改或扩大处理。

成功标准：恢复来自真实产品/流程改变和可验证证据，传播负责让改变被理解。
```

## E｜危机桌面推演 + 最终验收
```text
对方案做一次桌面推演【Tabletop Exercise】：
情境 1：新证据显示影响范围扩大；
情境 2：媒体拿到与公司初始声明不一致的信息；
情境 3：一名高影响力用户发布负面实测；
情境 4：监管要求更严格行动；
情境 5：内部信息被提前泄露。

逐一写：谁决策、30 分钟内做什么、哪些信息更新、哪些渠道暂停、下一次用户通知是什么。

最终检查普通用户是否能在 20 秒内知道：发生了什么 / 我是否受影响 / 我现在该做什么 / 公司正在做什么 / 什么时候再更新。
```

## 注意避免
- 在事实未确认前给绝对保证；
- 只关注舆情热度，忽略安全/补救；
- 多个部门各自发不同口径；
- 更新时偷偷删除旧说法，不解释变化；
- 在产品/流程没有改变前急于做“品牌修复 Campaign”；
- 用第三方背书替代真实调查方法。
